# LogLens 消费吞吐、SSE 顺序与多 Worker 取舍

> 状态：架构讨论记录，尚未改变当前实现。本文记录当前吞吐瓶颈、SSE 与顺序约束的关系，以及改为数据库增量轮询后多 Worker 的可行边界。性能数字是本机基准结果，不构成跨环境保证。

## 1. 结论

当前日志采集速度主要受单个消费线程串行处理和逐条落盘影响。SSE 不是已测出的主要吞吐瓶颈，但“实时推送必须全局有序”会给多 Worker 增加排序、合并和缺口处理逻辑。

对于单机个人面板，可以考虑由浏览器定时按数据库序号增量查询，数据库作为事实来源。这样可以让处理阶段按分区并行，而不要求 Worker 的完成顺序直接等于前端推送顺序。SQLite 仍只有一个有效写入者，因此并行化处理阶段不会自动把数据库写入吞吐按 Worker 数量线性放大。

若采用多 Worker，推荐顺序为：

```text
采集事件 → 按稳定 key 哈希分区 → 多 Worker 处理
                                   ↓
                         单个 SQLite 写入者
                         分配持久化序号并提交
                                   ↓
                   浏览器按序号定时增量查询
```

## 2. 当前处理路径和速度上限

`ProcessingRuntime` 使用一个 Disruptor RingBuffer，生产者为 MULTI，事件由一个 `loglens-consumer` 消费。日志、遥测、窗口刷新和关闭控制事件都经过这条消费路径。日志事件在进入队列前还会做快照脱敏；队列满时，默认 `DROP_NEWEST` 立即拒绝新的采集副本。配置的 RingBuffer 容量为 8192。

单个消费者处理日志时，至少会依次完成以下工作：

1. 将原始采集事件序列化并追加到 captured JSONL，再向 SQLite 写采集索引。
2. 执行字段提取、模板识别、重复折叠、关联和高亮等处理器。
3. 对处理结果追加 processed JSONL，写 SQLite 记录和标签索引，并按配置追加文本日志。
4. 存储成功后才把处理结果交给 SSE EventHub。

这意味着一个事件的 JSON 序列化、文件追加和 SQLite 操作都在消费线程上串行推进。SQLite 使用 WAL 和 `synchronous=NORMAL`，但 WAL 主要改善读写并发；SQLite 的写事务仍然串行。采集事件和遥测事件各自逐条插入，处理记录逐条开启事务并提交。增加处理 Worker 之前，应先确认 CPU 处理链是否比 SQLite/文件写入更慢；如果写入才是瓶颈，多个处理 Worker 最终仍会排队等同一个 SQLite 写入者。

Proxy Remote 的流量采样会进一步增加事件量：默认每秒为每个活动会话产生一条累计流量快照，另有连接和会话生命周期事件。近似采样量为“活动会话数 ÷ 采样间隔秒数”，例如 500 个活动会话、1 秒采样约产生 500 条遥测事件/秒。

### 队列满时的含义

8192 是可暂存的在途事件数，不是整个进程的总处理数。消费者处理一条就会释放一个槽位，长期吞吐取决于消费者能否赶上生产速度。若短时间的生产速率高于消费速率，8192 个槽位会被填满：

- `DROP_NEWEST`：保护应用日志调用线程，但 LogLens 不采集新到事件；应用原有 Appender 仍继续输出。
- `BLOCK`：在队列满时等待消费者，降低丢弃概率，但日志调用线程会被存储速度反向限速。它不能用于可能阻塞代理关键线程的遥测入口；遥测发布本身保持非阻塞，队列满时会计入遥测丢弃。

扩大 RingBuffer 可以缓冲更长的短时突发，但不会增加 SQLite 或消费者的持续处理速度，并会占用更多内存。

## 3. 本机基准结果

使用项目固定种子基准脚本，对 100,000 条短日志负载连续执行三轮。环境为 Windows 10、JBR 21.0.6、20 个逻辑处理器，RingBuffer 为 8192，结构化 JSONL/SQLite 开启。原始应用 FileAppender 在各轮均完整写入 100,000 行。

### 默认丢弃策略

| 模式 | 应用线程发起日志调用速度 | LogLens 采集数 | LogLens 丢弃数 | 采集调用 p99 |
|---|---:|---:|---:|---:|
| 原始应用，无 Agent | 198,613–204,540 次/秒 | — | — | 16.5–18.4 微秒 |
| Agent `observe` | 96,922–101,548 次/秒 | 8,543–8,695 条 | 91,305–91,457 条 | 51.7–58 微秒 |
| Agent `replace-console` | 58,112–59,419 次/秒 | 16,572–16,708 条 | 83,292–83,428 条 | 78–80.3 微秒 |

这里的“日志调用速度”是应用线程完成 100,000 次 Logger 调用的速率，不是 LogLens 无丢失持久化速率。默认策略允许生产线程快速前进，所以调用速率高时，队列满后的事件会被丢弃。`observe` 下应用原有 FileAppender 仍保存全部日志；丢失的是 LogLens 的采集副本。

### 阻塞、零丢弃参考

另以临时基准副本将策略改为 `BLOCK`，重复三轮。三轮都将 100,000 条原始事件完整写入 LogLens，丢弃数为 0：

| 模式 | 实测无丢弃调用速率范围 | 三轮中间值 | p99 调用耗时范围 |
|---|---:|---:|---:|
| `observe` | 2,990–7,746 条/秒 | 4,062 条/秒 | 50.3–152.5 微秒 |
| `replace-console` | 3,070–5,489 条/秒 | 3,104 条/秒 | 76.3–236.1 微秒 |

这组数据表示该机器、该短消息负载、当前处理器和存储配置下，开启阻塞后日志调用线程大致被限速到每秒数千条，同时 100,000 条最终全部被采集。三轮间波动明显，因此中间值只能作为容量规划参考，不能称为“保证值”。真实堆栈、MDC、磁盘、JVM 调度和业务日志模式都可能改变结果。

测试代码和此前已入库的三模式基准记录见 [benchmark-modes.py](../../LogLens/scripts/benchmark-modes.py) 与 [SDD 性能验证记录](../../LogLens/docs/sdd/verification.md#固定种子-100000-条三模式性能实测)。本次 `BLOCK` 测试仅修改 `.build` 下的临时脚本，没有更改项目源码或默认配置。

## 4. SSE 的作用和顺序成本

SSE 的优点是低延迟推送、空闲时不需要浏览器重复请求。当前 `EventHub` 为每个客户端维护有界 FIFO 队列，消费线程在存储成功后发布事件，客户端慢到队列满时会被标记为 gap 并断开。当前单消费者天然给处理结果提供了单一发布顺序。

这套实现里的 SSE 发布本身主要是向订阅者队列投递，不会在日志消费线程中逐个等待浏览器网络写入。因此没有基准证据表明 SSE 广播是当前每秒数千条吞吐的主因。移除 SSE 的直接收益更可能是减少订阅、水位、重连、gap 和全局推送顺序的架构约束，而不是立刻获得数量级的写入提升。

一旦处理改成多个 Worker，事件可能按不同速度完成。若仍要求 SSE 按全局输入顺序推送，就必须增加全局序号、重排缓冲或水位屏障；慢分区会阻挡已完成的后续事件，缓冲区也必须有界，并定义满载时的背压或丢弃行为。这就是 SSE 严格有序和多 Worker 并行之间需要额外协调的部分。

## 5. 数据库轮询与多 Worker 的建议边界

若浏览器改为每秒请求一次新增数据，查询以数据库提交结果为准：客户端携带上次序号，服务端执行类似 `WHERE seq > ? ORDER BY seq LIMIT ?` 的 keyset 查询。若单次限制内未取完，客户端继续用下一页游标追赶。请求返回的数据天然按持久化序号读取，页面不再依赖 worker 完成顺序，也无需维护每个浏览器的实时推送队列。

需要明确，“数据库中的顺序”不是 SQLite 自动定义的物理行顺序，必须由持久化序号和 `ORDER BY` 明确规定。多 Worker 并行时可采用以下语义：

- 持久化序号由单个 SQLite 写入者在提交路径上分配，表示数据库接受并提交的顺序。轮询按此序号读取。
- 原始采集序号单独保留，用于诊断采集顺序和处理延迟。若业务仍要求严格按原始采集序号入库，则必须在写入前合并并等待缺失序号，部分并行收益会被顺序屏障抵消。
- 日志处理记录和连接遥测当前使用不同序号域。若 UI 分开呈现，可分别维护游标；若需要混合时间线，应在存储模型中增加统一的持久化事件序号，不能直接比较两个独立水位。

推荐先并行化 CPU 密集且可按 key 隔离的处理阶段，再由单个 SQLite 写入者完成持久化并分配序号。哈希分区应让同一折叠/关联 key 落到同一 Worker；对全局状态处理器，需改为分区状态、线程安全状态或保留串行阶段。不能把一个 Disruptor RingBuffer 简单划成多个槽位集合后就认为顺序、状态和存储都已解决。

轮询的取舍如下：

| 方面 | SSE 推送 | 数据库增量轮询 |
|---|---|---|
| 更新延迟 | 事件提交后即可推送 | 通常不超过轮询间隔，例如约 1 秒 |
| 空闲开销 | 持有长连接和服务端订阅状态 | 周期性 HTTP 请求和少量只读查询 |
| 顺序定义 | 广播路径需要维护顺序和 gap | 使用数据库序号及 `ORDER BY` |
| 断线恢复 | 需要水位、重连和历史补齐 | 记录上次游标后继续查询 |
| 多 Worker 适配 | 全局实时推送常需重排/屏障 | Worker 完成顺序与浏览器读序解耦 |
| 主要限制 | 慢客户端队列溢出 | 轮询频率、只读查询负载和追赶分页 |

对单机、少量浏览器客户端的个人面板，约 1 秒轮询的延迟通常比维护全局 SSE 顺序约束更划算。仍需使用有界 HTTP 执行器、查询条数上限和游标分页，避免并发轮询或历史积压占满 Web 线程。

## 6. 推荐决策与未决问题

1. 当前 SQLite、JSONL 和处理器链已满足个人连接监控与排障需求，不因理论扩展提前引入消息队列或 Elasticsearch。
2. 若决定进一步并行化，优先评估“数据库增量轮询 + 按 key 分区的处理 Worker + 单 SQLite 写入者”。持久化序号是 UI 的顺序依据。
3. 不把 SSE 删除描述为吞吐优化结论，除非有关闭 SSE 与启用 SSE 的同机对照基准证明其占比；现有基准没有做该对照。
4. 实施前应按 LogLens SDD 更新需求、设计、任务和验收证据，特别是顺序语义、分区 key、状态型处理器、满载背压、轮询间隔、掉线追赶和多游标模型。

仍需回答的工程问题包括：预期最大活跃连接/会话数和日志峰值、折叠与关联状态如何分区、Telemetry 与 processed logs 是否合并为统一时间线，以及轮询的默认频率与最大追赶页数。性能目标应在目标服务器、真实日志尺寸和真实活跃会话数下重新测量后确定。
